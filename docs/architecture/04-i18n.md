# 04 Internationalisation

## 1. Library choice

[`fluent-rs`](https://github.com/projectfluent/fluent-rs) (Mozilla Fluent). Reasons:

- First-class support for complex plurals (`one`, `few`, `many`, `other` in CLDR plus language-specific rules).
- Selectors for tone, gender, and arbitrary application-defined keys.
- The `.ftl` format is human-friendly for translators; we can hand a single file to a contractor and get usable output back.
- BCP-47 language tags via `unic-langid`.

## 2. File layout

```
locales/
├── ja-JP/
│   ├── commands.ftl
│   ├── notifications.ftl
│   ├── errors.ftl
│   └── setup.ftl
└── en-US/
    ├── commands.ftl
    ├── notifications.ftl
    ├── errors.ftl
    └── setup.ftl
```

The same set of namespaces and the same set of message keys exist in every locale directory. A CI job (`i18n-keys`) diffs the keysets and fails if they differ.

## 3. Locale resolution order

For every user-facing string the bot resolves a locale in this order:

1. **User Discord locale** — `Interaction.locale` field from Discord (only available on interactions, not on raw gateway events).
2. **Guild default locale** — `guild_settings.locale` set via `/config set locale`.
3. **Fallback** — `en-US`.

For non-interaction outputs (scheduler notifications, active-tasks message), only steps 2 and 3 apply since there is no user context.

## 4. `Translator` port

```rust
pub trait Translator: Send + Sync {
    fn t<'a>(&self, locale: &Locale, key: &str, args: TArgs<'a>) -> String;
}
```

Where `TArgs<'a>` is a small wrapper over `&[(&'a str, FluentValue<'a>)]`. The implementation in `core_infra` is `FluentTranslator`, which loads all `.ftl` files at startup, builds one `FluentBundle` per locale, and looks up messages on each `t` call.

### 4.1 Macro

```rust
let msg = tr!(translator, locale, "config-set-role-success", role = role.name());
```

The `tr!` macro lives in `core` (no external macro crate). It expands to a call to `Translator::t` with arguments wired up.

### 4.2 Missing-key behaviour

- Production: log a `tracing::warn!` and return the key string. We never panic on a missing translation.
- Tests: panic by default; a `Translator::strict` flag for tests promotes warnings to errors.

## 5. Key naming

- Kebab-case: `task-state-not-started`, `notification-stale-task-summary`.
- Domain prefix: `config-`, `task-`, `notification-`, `error-`, `setup-`.
- `error-` keys map 1:1 to `thiserror` variants. The renderer that turns an error into a Discord embed has a static `fn key_for(&Error) -> &'static str`.

## 6. Sample `.ftl`

`locales/ja-JP/notifications.ftl`:

```ftl
notification-stale-task-summary = {$role} 以下のタスクが {$days} 日間放置されています:
notification-stale-task-item    = - {$title}（{$state}・最終更新 {DATETIME($changed_at)}）
notification-no-stale           = 放置されているタスクはありません。
```

`locales/en-US/notifications.ftl`:

```ftl
notification-stale-task-summary = {$role} the following tasks have been idle for {$days} days:
notification-stale-task-item    = - {$title} ({$state}, last changed {DATETIME($changed_at)})
notification-no-stale           = No stale tasks.
```

## 7. Plural handling

Fluent's `select` keeps plural variants in the translator, not in the call site:

```ftl
task-count = {$count ->
    [one]   {$count} task
   *[other] {$count} tasks
}
```

The Japanese version simply omits the plural branch since Japanese is not pluralised:

```ftl
task-count = {$count} 件のタスク
```

## 8. Date/number formatting

Fluent's built-in `DATETIME(...)` and `NUMBER(...)` are used. They route through `intl-memoizer` and respect the locale's CLDR rules. We do not format dates by hand in Rust.

## 9. Bot UI surface

All slash command descriptions and option descriptions are also localised. Twilight accepts `name_localizations` and `description_localizations` maps on command registration; we generate them by iterating known locales.

## 10. Adding a new locale

1. `cp -r locales/en-US locales/zh-CN`
2. Translate the values.
3. Add `zh-CN` to the `SUPPORTED_LOCALES` array in `core/src/i18n/mod.rs`.
4. `cargo test -p core_infra` verifies key parity.
